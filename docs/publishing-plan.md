# 공개 계획 (Publishing Plan)

첫 버전은 글쓴이 컴퓨터에서만 실행합니다. 이 문서는 나중에 인터넷에 공개할 때 고를 선택지와 순서를 적은 것입니다. 지금 정할 것은 없고, 공개하기로 할 때 글쓴이가 고릅니다.

근거: 요구사항 FR12.1, FR12.2, NFR7, 설계 결정 ADR-002(SQLite), ADR-003(사진 폴더), ADR-006(글쓴이 판단), 팀 개발 방식의 Deployment 항목.

> 가격과 무료 범위는 이 문서를 쓴 시점(2026년 11월)에 알고 있던 값을 적은 것입니다. 서비스마다 자주 바뀌므로 공개 전에 각 서비스의 가격 안내를 다시 확인해야 합니다. 원화 금액은 1달러를 약 1,400원으로 어림한 값입니다.

## 1. 지금 상태

| 항목        | 지금                                                 | 공개할 때 문제                                                                           |
| ----------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 글 저장     | 프로젝트 안 SQLite 파일 `data/blog.db`               | 서버리스 호스팅(Vercel 등)은 로컬 파일에 저장할 수 없습니다                              |
| 사진 저장   | 프로젝트 안 `uploads/` 폴더                          | 서버리스 호스팅은 올린 파일이 남지 않습니다                                              |
| 글쓴이 판단 | 이 컴퓨터(루프백)에서 `localhost`로 연 요청만 글쓴이 | 인터넷에서는 모든 요청이 프록시를 거쳐서 이 판단이 맞지 않습니다. 로그인이 꼭 필요합니다 |
| 실행        | `server.ts`(Node 서버)                               | 서버리스 호스팅은 직접 만든 서버를 쓰지 않습니다                                         |

| 후보               | 구성                                                                                            | 바꿀 코드                                                                                 | 맞는 경우                                      |
| ------------------ | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------- |
| A. 서버리스        | Vercel(화면과 서버 기능) + Turso(SQLite와 호환되는 클라우드 데이터베이스) + Cloudflare R2(사진) | 데이터베이스 연결 주소, 사진 저장 위치(Media), 로그인, `server.ts` 대신 Next.js 기본 실행 | 서버 관리 없이 시작하고 싶을 때                |

추천: 처음에는 **B(작은 서버 하나)** 가 바꿀 코드가 가장 적습니다. 방문이 늘거나 서버 관리가 귀찮아지면 A로 옮깁니다.

- 도메인 이름을 쓰면 해마다 1~3만 원이 따로 듭니다.

## 4. 저장 방식 옮기기 (NFR7)

### 글: SQLite에서 Turso 또는 Postgres로

- **Turso(추천)**: SQLite와 같은 형식이라 표를 그대로 씁니다. 앱은 이미 `@libsql/client`로 연결하므로 `src/lib/db/client.ts`에서 `createClient`에 인증 토큰(`DATABASE_AUTH_TOKEN` 같은 환경 변수)을 더하고, `DATABASE_URL`을 `libsql://...` 주소로 바꾸면 됩니다. 기존 글은 `turso db create --from-file data/blog.db` 같은 명령으로 파일째 올립니다(명령은 Turso 안내에서 확인).
- **Postgres(Supabase, Neon 등)**: Drizzle 표 정의(`src/lib/db/schema.ts`)를 Postgres용(`pg-core`)으로 바꾸고, 태그 검색에 쓰는 `json_each`를 Postgres의 `jsonb` 연산으로 바꿔야 합니다. 바꿀 곳이 많아 Turso보다 손이 갑니다.

### 사진: 폴더에서 R2(또는 S3)로

- 사진을 쓰고 읽고 지우는 코드는 `src/lib/media/service.ts` 한 곳에 모여 있습니다(ADR-004). 이 파일의 파일 쓰기(`writeFile`, `rename`)와 지우기를 R2 업로드와 삭제로 바꿉니다. R2는 S3와 같은 방식으로 쓸 수 있습니다.
- 내보내기 경로 `/media/[id]/[width]`는 R2 공개 주소(또는 CDN 주소)로 바꾸고, `src/lib/media/rules.ts`의 `photoUrl`만 고치면 화면 전체가 새 주소를 씁니다.
- 기존 사진은 `uploads/variants/`와 `uploads/originals/` 폴더를 그대로 올립니다. 파일 이름이 사진 id라 그대로 맞습니다.
- 사진 줄이기(sharp)는 Node 서버가 필요합니다. A나 B에서는 그대로 쓸 수 있고, C에서는 다른 방식이 필요합니다.

## 5. 공개 순서

1. 공개 방식(아래 6절)과 호스팅 후보(2절)를 고릅니다.
2. 글쓴이 로그인을 만듭니다(7절 첫 항목). 로그인이 없으면 공개하지 않습니다.
3. 공개용 설정에서 `BLOG_PUBLIC_MODE=1`로 루프백 판단을 끄고, 로그인으로 글쓴이를 판단하도록 바꿉니다.
4. 저장 방식을 옮깁니다(4절). 먼저 시험용 주소에서 확인합니다.
5. 지금 글과 사진을 옮기고, 시험용 주소에서 글 본문, 사진, 검색, 비공개 글이 독자에게 안 보이는지를 확인합니다.
6. 실제 주소로 공개합니다. 문제가 생기면 바로 앞 버전으로 되돌립니다(호스팅의 이전 배포로 되돌리기).

## 6. 공개 방식 선택지

글쓴이가 Q6에서 나중에 정하기로 했습니다(D). 셋 중 하나를 고릅니다.

| 선택지                              | 내용                                                                                          | 좋은 점                                   | 신경 쓸 점                                          |
| ----------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------- | --------------------------------------------------- |
| 1. 시험용 자동, 실제 공개는 승인 뒤 | `main`에 합칠 때마다 시험용 주소에 자동으로 올리고, 실제 공개는 글쓴이가 승인한 뒤에만 합니다 | 실수가 실제 사이트에 바로 나가지 않습니다 | 공개할 때마다 승인 한 번이 필요합니다               |
| 2. 실제 공개까지 자동               | `main`에 합칠 때마다 실제 사이트까지 자동으로 올립니다                                        | 가장 빠르고 손이 안 갑니다                | 자동 검사(GitHub Actions)가 실패를 잘 잡아야 합니다 |
| 3. 매번 직접                        | 글쓴이가 명령을 직접 실행해 올립니다                                                          | 언제 나가는지 완전히 정할 수 있습니다     | 잊기 쉽고 손이 많이 갑니다                          |

어떤 선택지든 GitHub Actions의 검사(`npm run check`와 같은 내용)가 실패하면 올리지 않습니다.

## 7. 공개 전 확인 항목

- [ ] **글쓴이 로그인 만들기 (필수, FR12.2)**: 첫 버전에는 로그인이 없습니다. 비밀번호나 외부 계정 로그인(예: GitHub 로그인)을 만들고, 모든 쓰기 기능(저장, 발행, 지우기, 사진 올리기)과 글쓴이 화면이 로그인을 확인하게 합니다. `src/lib/access/author.ts`의 판단을 로그인 확인으로 바꾸는 것이 시작점입니다.
- [ ] **루프백 판단 끄기**: 공개 설정에서 `BLOG_PUBLIC_MODE=1`을 둡니다. 이 값이 있으면 이 컴퓨터에서 연 요청도 글쓴이로 보지 않아, 로그인 없이는 글을 쓸 수 없습니다.
- [ ] 데이터 파일과 사진 폴더가 공개 저장소(git)에 올라가지 않았는지 확인합니다.
- [ ] 비공개 글과 임시 저장 글이 첫 화면, 모아보기, 검색, 글 주소에서 독자에게 보이지 않는지 시험용 주소에서 확인합니다.
- [ ] 사진이 휴대폰(빠른 4G 수준)에서 제목과 첫 사진 3초 안에 보이는지 확인합니다(NFR1).
- [ ] 백업 방법을 정합니다(데이터베이스 내보내기, 사진 저장소 복제).
- [ ] 사이트 이름(`NEXT_PUBLIC_SITE_NAME`)을 정합니다.
- [ ] 글꼴 파일을 사이트에 함께 올릴지 정합니다(지금은 Google Fonts에서 받아 옵니다).
- [ ] **패키지 취약점 정리**: 2026-11-05 `npm audit` 기준으로, 앱이 쓰는 패키지에 높음(high) 등급 4개가 있습니다. drizzle-orm(0.45.2 이상), sharp(0.35.5 이상), next가 쓰는 postcss(next 16), zod(4.6.6 이상)입니다. 모두 큰 버전 올리기라 공개 전에 하나씩 올리고 테스트와 브라우저 확인을 다시 돌립니다. 지금 CI는 앱 패키지의 심각(critical) 등급만 실패로 처리합니다.
- [ ] **테스트 실행기 올리기**: Vitest 3.2.7이 쓰는 tinypool에 심각(critical) 등급 2개가 있습니다. 개발할 때만 쓰는 패키지라 사이트에는 들어가지 않지만, Vitest 4.1.12 이상으로 올려 없앱니다(`@vitest/coverage-v8`도 같은 버전으로).
